# Roadmap pragma.core

Принцип: **вертикальный срез раньше ширины**. Уже к M3 пример `frame_sim` проходит через все слои:
пул → граф кадра → async-загрузка → детерминированный результат. Каждую следующую веху проверяем
на нём, а не на изолированных микротестах.

## M1 — Job system (0.1.0)

**Цель:** пул, на котором можно параллелить реальную работу кадра без дедлоков и потерь паник.

`pragma_sync`
- [x] `Parker`/`Unparker` для сна воркеров (адресное пробуждение, без потерянных wakeup)
- [x] `AtomicCounter`, на котором ждут задачи («ждать счётчик до нуля» вместо хэндла на каждую задачу)
- [x] loom-модели: латч, парковка, счётчик

`pragma_jobs`
- [x] `ThreadPool::new(PoolConfig) -> Result`, именованные потоки, корректный `Drop` (join всех потоков)
- [x] Work-stealing: локальные `crossbeam_deque::Worker` + `Injector` + кража у случайной жертвы
- [x] `spawn` → `JobHandle<T>` с `join() -> Result<T, JobError>`
- [x] `join(a, b)` с help-while-wait; вложенный `join` на 1 воркере не дедлочит
- [x] `scope(|s| ...)` с заимствованием данных (без `'static`)
- [x] `parallel_for` / `parallel_for_chunks` с `Grain::{Auto, Fixed(n)}`; детерминированная редукция (`parallel_reduce`)
- [x] Перехват паник → `JobError::Panicked { job, message }`
- [x] Приоритеты `Frame` / `Normal` / `Background` + лимит воркеров для `Background`

Тесты и бенчи
- [x] proptest: `parallel_for` равен последовательному циклу; вложенные `scope` на случайной глубине
- [x] Стресс (`#[ignore]`, в CI ночью): 10⁷ мелких задач, случайные паники, 1..2N воркеров
- [x] `criterion`: spawn/join overhead, `parallel_for` на 10⁶ элементов, сравнение с `rayon`

**Готово, когда:** всё выше зелёное на Windows и Linux; накладные расходы spawn+join ≤ 2× от
`rayon::join`; при панике в задаче процесс не падает и ничего не виснет; `Drop` пула не оставляет потоков.

**Состояние критериев** (Windows, AMD FX-8350, 8 логических ядер — ранее ошибочно «12 потоков», см. `docs/perf.md`, `cargo bench -p pragma_jobs`):

| Критерий | Состояние |
|---|---|
| Зелёное на Windows и Linux | Локально Windows; Linux — в CI PR |
| Паника не роняет процесс, ничего не виснет | ✅ тесты `pool.rs` + стресс `random_panics_never_hang_or_kill_workers` |
| `Drop` не оставляет потоков | ✅ `Drop` join-ит все потоки; стресс 500 циклов создания/удаления |
| Одиночный `join` ≤ 2× rayon | ✅ 0.65 µs против 1.86 µs |
| Вложенный fork-join (fib(20), ~11k `join`) ≤ 2× rayon | ✅ в M4b: 197–200 µs против 99–108 µs (1.95–1.99×; было 0.56 ms против 0.12 ms, 4.6×), DECISIONS #30, `docs/perf.md` |
| `parallel_for` / редукция на 10⁶ | ✅ 0.51 / 0.30 ms против 0.61 / 0.34 ms у rayon |

## M2 — Граф кадра (0.2.0)

- [x] `FrameGraph::builder()`: задачи с объявлением `reads::<T>()` / `writes::<T>()` и явным `before`/`after`
      (+ режим `ordered`: конфликт упорядочивается порядком объявления)
- [x] `build()`: циклы → `GraphError::Cycle`, неявный конфликт → `AmbiguousOrder`, неизвестная зависимость
      → `UnknownDependency`, дубль имени → `DuplicateTask`
- [x] Стабильная топосортировка; `run()` без аллокаций в установившемся режиме (тест `tests/alloc.rs`)
- [x] Хранилище ресурсов с безопасным раздельным доступом (типизированные слоты, проверка заимствований при сборке графа)
- [x] Вложенный параллелизм: задача графа может вызвать `parallel_for`
- [x] Экспорт графа в DOT/Mermaid для отладки
- [x] Fuzz: произвольные описания графа → либо ошибка, либо корректный порядок (`fuzz/`, тот же оракул в proptest)
- [x] CI: `cargo hack --each-feature`

**Готово, когда:** граф из ~50 задач строится один раз и исполняется за кадр без аллокаций;
любой конфликт без порядка ловится в `build()`.

**Состояние критериев** (Windows, AMD FX-8350, 8 логических ядер — ранее ошибочно «12 потоков», см. `docs/perf.md`):

| Критерий | Состояние |
|---|---|
| ~50 задач, кадр без аллокаций | ✅ `tests/alloc.rs`: 50 задач, 0 аллокаций за 2000 кадров на 1/2/4 воркерах (debug и release) |
| Любой конфликт без порядка ловится в `build()` | ✅ `AmbiguousOrder` до первого кадра; proptest + fuzz против независимого оракула; в кадре доступ к ресурсам ни разу не конфликтует |
| Зелёное на Windows и Linux | Локально Windows; Linux, fuzz и `cargo hack` — в CI PR |
| Производительность (`cargo bench -p pragma_graph`, 50 задач, две независимые цепочки) | Работа 4096 эл./задачу: 313 µs против 714 µs последовательно; почти пустые задачи: 9.2 µs против 2.8 µs — ~130 ns планирования на задачу |

## M3 — Async-задачи и вертикальный срез (0.3.0)

- [x] Executor на `async-task`: `spawn_async(fut) -> AsyncHandle<T>`, планирование в пул с приоритетом `Background`
      (через `pragma_jobs::Spawner`, DECISIONS #24)
- [x] Blocking-пул для синхронного файлового I/O (ограниченный размер): `Executor::unblock`, I/O-модель — DECISIONS #23
- [x] Отмена через drop хэндла, паника → `AsyncError::Panicked`
- [x] Мост в кадр: `poll_ready()` (+ `.await` на хэндле), без `block_on` в задачах кадра — `wait()` из работы
      пула возвращает `WouldBlock` (DECISIONS #25)
- [x] **Пример `examples/frame_sim`**: headless-цикл с фиксированным шагом, 100k «сущностей»,
      граф из 9 систем, фоновая «загрузка» через async, хеш состояния на каждом тике
- [x] `frame_sim` запускается в CI на N тиков и сверяет хеш на 1 и N воркерах

**Готово, когда:** `frame_sim` стабильно работает в CI на обеих ОС, хеш совпадает.

**Состояние критериев** (Windows, AMD FX-8350, 8 логических ядер — ранее ошибочно «12 потоков», см. `docs/perf.md`):

| Критерий | Состояние |
|---|---|
| `frame_sim` в CI на обеих ОС, хеш совпадает на 1 и N воркерах | Локально Windows: `--ticks 300 --verify 1,4,11` — хеш всех 300 тиков совпадает в 6 прогонах; Windows и Linux — шаг CI `--verify 1,4` в PR |
| Результат не зависит от момента завершения загрузки | ✅ загрузка применяется на тике 60 (DECISIONS #26); `--verify` прогоняет и «успела» (готова на тике 1), и «не успела» (250 мс, главный поток ждёт между кадрами) — хеши равны; тест `background_load_affects_state_from_apply_tick` подтверждает, что загрузка влияет на состояние |
| Отмена без утечек и зависаний | ✅ `tests/executor.rs`: сброс до старта, во время `poll`, в ожидании, после завершения; счётчик `Drop`; остановка пула и исполнителя — `Cancelled` без зависания |
| Паника → `AsyncError::Panicked`, воркер жив | ✅ на 1 воркере, для `spawn_async` и `unblock` |
| Blocking-пул: лимит, переполнение не блокирует | ✅ пик ≤ лимита потоков; сверх `blocking_capacity` — `Overloaded` сразу; воркеры пула свободны, пока blocking-поток занят |
| Стресс | ✅ proptest (случайная отмена/паники/blocking, 1–3 воркера) + `#[ignore]` 200k задач на 1..2N воркерах (0.5 с), ночной CI |
| Производительность `frame_sim` (100k сущностей, release) | 1 воркер — ~5 мс/тик, 4 — ~2.4 мс, 11 — ~2 мс |

## Вне скоупа (пересматривается только через DECISIONS.md)

- ECS, рендер, окно/ввод, App/плагины, сеть: это задачи движков поверх ядра
- Защита от падений на уровне процесса (крэш-репортер, минидампы, автосохранение, супервизор):
  политика приложения; ядро даёт только контекст для неё (M4), см. [reliability.md §4](reliability.md#4-деградация-вместо-падения)
- wasm / macOS / мобильные: API их не исключает, но поддержка — отдельная веха после 1.0
- Файберы/корутины на своих стеках: много `unsafe` и платформенного ассемблера; help-while-wait решает ту же проблему
- Свои lock-free структуры вместо crossbeam (DECISIONS #5)
- Tracy (C++): только за feature-флагом и по отдельному решению

## Риски

| Риск | Митигирование |
|---|---|
| Дедлоки во вложенных `join`/`scope` | help-while-wait по построению; стресс-тесты на 1 воркере |
| Потерянные пробуждения при парковке | loom-модели до мержа; таймаут-страховка при парковке |
| `scope` с заимствованиями требует `unsafe` (стирание лайфтайма) | Изолировать в `pragma_sync`, Miri; изучить подход `std::thread::scope`/rayon |
| Фоновые задачи вытесняют кадр | Лимит воркеров для `Background`, бенч «кадр под нагрузкой» |
| Рост скоупа (ECS «раз уж ядро») | Раздел «Вне скоупа» + DECISIONS #1 |
