# Производительность: методика и результаты

Как мерить производительность pragma.core так, чтобы цифрам можно было верить, и что намерено.
С M5 та же методика автоматизирована бенч-гейтом в CI (§6); ручные замеры — для решений о
тюнинге и для таблиц ниже.

## 1. Железо и окружение

| | |
|---|---|
| CPU | AMD FX-8350, 4 модуля / **8 логических ядер** (`available_parallelism() = 8`) |
| RAM | 18 ГБ |
| ОС | Windows 10 Home, системный аллокатор (~90 нс на аллокацию) |
| Тулчейн | Rust 1.99.0 (`rust-toolchain.toml`), профиль `bench` = `release` + `debug = true`, `lto = "thin"`, `codegen-units = 1` |

В таблицах roadmap для M1–M3 машина была ошибочно указана как «12 потоков»; это та же машина
с 8 логическими ядрами. Поэтому `frame_sim --workers 11` (и `--verify 1,4,11`) — режим с
переподпиской: 11 воркеров плюс главный поток на 8 ядрах.

## 2. Команды

```bash
cargo bench -p pragma_jobs            # join, fib(20), scope, spawn, parallel_for/reduce против rayon
cargo bench -p pragma_graph           # граф 50 задач против последовательного исполнения
cargo bench -p pragma_async           # перепланирование async-задачи и цена Box в нём
cargo run -p frame_sim --release -- --ticks 300 --verify 1,4,11   # мс/тик = время / 300 (latency=0ms)
```

Пулы в `pragma_jobs` бенчах — одного размера с rayon: `with_workers(available_parallelism())`.
В pragma главный поток ещё и участвует в работе (внешний слот), в rayon он ждёт в `install`.

## 3. Правила замера

1. **A/B вперемешку.** Машина «плавает» между сессиями на десятки процентов (тепло, фоновые
   процессы): `frame_sim` на 11 воркерах в один день давал 530 и 660–720 мс на одном и том же
   коде. Сравниваем только прогоны, сделанные подряд в одних условиях: ветка → `main` → ветка →
   `main` (`git stash -u` / `git stash pop`), минимум **2 круга**.
2. **Во время замера машина свободна.** Никакой сборки, тестов и Miri параллельно.
3. **Разброс.** Criterion даёт интервал по 100 выборкам; между прогонами смотрим на
   *эталон* — rayon в тех же прогонах без изменений кода. Если rayon сдвинулся на X%, то
   изменение pragma меньше X% — шум. В замерах M4 rayon сдвигался до ±8% (fib(20) 99–108 µs,
   редукция 230–282 µs).
4. **Детерминизм проверяется на каждом прогоне** (`frame_sim --verify`): перф-изменение,
   сломавшее хеш, не принимается.
5. Колонку `change:` из criterion не используем: она сравнивает с последним прогоном
   *любого* кода, а не с базовой линией.

- **Вложенный `join` ≤ 2× rayon — выполнено**: 1.95–1.99× (было 4.6–5.5×). Причина ускорения

- Остальное — без изменений сверх шума; хеш `frame_sim` совпал во всех прогонах.

### Перебор `idle_spin` (DECISIONS #32)

Один прогон на значение (`--measurement-time 3`), одинаковые условия:

| `idle_spin` | fib(20) | `scope` 1000 | `spawn`+`join` | `parallel_for` | `frame_sim` 4 / 11, мс за 300 тиков |
|---|---|---|---|---|---|
| 0 | 203 µs | 950 µs | 1.47 µs | 461 µs | 785 / 637 |
| 8 | 190 µs | 1037 µs | 1.30 µs | 464 µs | 873 / 665 |
| **32** (по умолчанию) | 203 µs | 906 µs | 1.33 µs | 451 µs | 783 / 669 |
| 128 | 203 µs | 964 µs | 1.61 µs | 446 µs | 785 / 710 |

Разница по fib(20) — в пределах шума; 32 лучше на `scope`, 128 ухудшает `spawn` и
переподписанный `frame_sim` (yield-ящие воркеры мешают главному потоку). 32 — как у rayon по
порядку величины; настройка открыта приложению (`PoolConfig::with_idle_spin`).

### `Box` на планирование async (DECISIONS #31)

`cargo bench -p pragma_async`: перепланирование задачи (`yield_now` → пул → `poll`) —
**1.39 µs**, `Box<dyn FnOnce>` (аллокация + вызов + освобождение) — **88 нс**, ~6%. Основная цена —
межпоточное пробуждение через глобальную фоновую очередь; `Box` оставлен.

## 6. Бенч-гейт в CI

`tools/bench_gate.py`, джоб `bench gate` в каждом PR на Windows и Linux (DECISIONS #34). Это
§3, автоматизированный:

1. Базовая ревизия (base PR, то есть `main`) — в `git worktree`. Обе ревизии собираются в
   разные target-каталоги до первого замера.
2. Замеры вперемешку: base → head, 3 круга. Каждый круг — criterion (`--warm-up-time 1
   --measurement-time 3`) по `join`, fib(20), `scope` 1000, `parallel_for`/`parallel_reduce`
   10⁶, граф 50 задач, и два запуска `frame_sim --ticks 300` на 1 и N = ядра − 1 воркерах.
   По каждому замеру берётся лучшее значение по кругам: шум общего раннера только замедляет.
3. Регрессия: `ratio = head / base`. У замеров с эталоном в том же бенче (rayon,
   последовательный код) `ref_ratio` — сдвиг эталона, на который pragma не влияет. Падение,
   если `ratio > 1.10` **и** `ratio / ref_ratio > 1.10`. `frame_sim` эталона не имеет и падает
   при `ratio > 1.10 + шум`, где шум — его собственный: 3 запуска на круг, медиана / минимум − 1
   по всем запускам каждой ревизии, наибольший из двух (DECISIONS #41; раньше — наибольший
   `|ref_ratio − 1|`, то есть шум наносекундного `rayon_single`).
4. fib(20) ≤ 2× rayon на голове PR — строка в summary и `::warning::`, не падение:
   отношение зависит от числа ядер.

Результат — таблица в summary джоба.

### Шум раннеров GitHub (PR #8: ubuntu — M5a против `main`, windows — M5a+M5b против M5a; код бенчей не менялся)

| | ubuntu-latest | windows-latest |
|---|---|---|
| Ядер (`os.cpu_count()`) | 2 | 2 |
| Наибольший сдвиг эталона | 21.9% (`rayon_single`, 124 ns) | 35.4% (`rayon_single`, ~145 ns) |
| Сдвиг остальных эталонов | ≤ 0.1% | ≤ 0.3% |
| `frame_sim` 1 воркер, head / base на одном коде | 1.152 (один запуск на круг) | 0.981 (лучший из двух на круг) |
| fib(20) pragma / rayon | 2.32× | 2.48× (локально на 8 ядрах — 1.98×) |

Выводы: criterion-замеры микросекундного масштаба на обоих раннерах стабильны (±0.3%), а
наносекундный `join` одиночный шумит на 20–35%, `frame_sim` (время с созданием пула, 3 потока на
2 ядрах) — до 15%. Поэтому `join/pragma_single` гейтится только с нормировкой на rayon, а порог
`frame_sim` раздувается шумом `rayon_single` (1.32 на ubuntu, 1.45 на windows): регрессию
`frame_sim` меньше ~30–45% гейт на 2-ядерном раннере не поймает. Это осознанный компромисс против ложных падений. Точные
замеры по-прежнему делаются вручную по §3.

**Обновление (DECISIONS #41):** шум `frame_sim` теперь оценивается по его же запускам, а не по
`rayon_single`, который с `frame_sim` никак не связан. Порог следует реальному разбросу
`frame_sim` на конкретном раннере, а не худшему наносекундному бенчу.
