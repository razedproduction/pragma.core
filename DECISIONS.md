# pragma.core decisions

ADR log. A decision changes only through a new entry with a reason (the old one is not deleted, it is marked "superseded by #N").

| # | Decision | Choice | Why | Date |
|---|---------|-------|--------|------|
| 1 | Core boundaries | A runtime core: base + sync + jobs + frame graph + async. **No** ECS, rendering, windowing, App/plugins | The core must suit different engines and frameworks; ECS and the frame loop are decisions of a specific engine and are built on top | 2026-10-13 |
| 2 | Platforms | Windows and Linux (x86_64), both in CI | The current targets. macOS/wasm/mobile are out of scope; the API must not rule out a single-threaded fallback (needed for wasm without atomics), but does not implement one either | 2026-10-13 |
| 3 | Audience | Own indie projects, with room for professional use | A simple API now; "pro" guarantees (determinism, semver-checks, bench gate, MSRV) are introduced in stages and are mandatory by v1.0, see the roadmap | 2026-10-13 |
| 4 | Dependency purity | Pure Rust only; system FFI (`windows-sys`, `libc`) is allowed | Reproducible builds, cross-compilation, auditing. Checked by `cargo deny`, `tools/audit_workspace.py` | 2026-10-13 |
| 5 | Lock-free foundation | `crossbeam-deque` / `crossbeam-utils` instead of our own lock-free structures | Pure-Rust code proven over years; our own Chase-Lev deque would mean months of verification for a few percent | 2026-10-13 |
| 6 | `unsafe` policy (refined by #27) | `#![forbid(unsafe_code)]` everywhere except `pragma_sync`; there, a `// SAFETY:` on every block, Miri + loom in CI | Confines the risk to one small crate that can actually be verified | 2026-10-13 |
| 7 | Purity exception | `generator` (pulls in `cc`) via `loom` is accepted (refined by #12) | Only a dev dependency under `cfg(loom)`, never reaches users' binaries; `deny.toml` excludes the dev graph | 2026-10-13 |
| 8 | Async executor | `async-task` + `futures-lite`, no tokio | The core needs an executor, not a network reactor; tokio means a second thread pool and heavy dependencies. The I/O model is chosen at milestone M3 | 2026-10-13 |
| 9 | Panics in tasks | Caught with `catch_unwind` in the worker and returned as errors from `join`/the handle | A panic in user code neither kills a worker nor hangs waiters. With `panic = "abort"` the process dies; this is documented | 2026-10-13 |
| 10 | Toolchain | Edition 2024, MSRV 1.88 (the minimum for proptest), pinned to 1.99.0 | Identical clippy results locally and in CI; the MSRV is checked by a separate job | 2026-10-13 |

| 13 | `pragma_jobs` errors | Two enums: `JobsError` (pool creation) and `JobError` (task outcome) | A task outcome needs to be cloned, compared and sent between threads, while `JobsError` carries a `std::io::Error` (not `Clone`). | 14 | Baseline in benches | `rayon` only as a dev dependency of `pragma_jobs` | Comparing overhead with the industry standard (roadmap M1). It never reaches users' dependency trees (`deny.toml: exclude-dev`) | 2026-10-13 |
| 15 | `unsafe` for `scope`/`join` | Lifetime erasure of scope tasks and the task-in-a-stack-slot (`StackSlot`) live only in `pragma_sync` (`scope.rs`) | `pragma_jobs` stays `forbid(unsafe_code)`: it gets a safe API where `scope()` does not return until all tasks have finished (a panic while waiting → `abort`). `StackSlot` removes the `Box` from `join`: on the Windows system allocator an allocation (~90 ns) costs more than the `join` itself | 2026-10-13 |
| 16 | The main thread in the pool | External slots: 4 LIFO queues that a thread outside the pool occupies for the duration of `scope`/`join`/`JobHandle::join` | Through the FIFO injector, helping while waiting would take the oldest tasks and grow the stack quadratically (fib(20) overflowed the stack in debug). An external thread does not take `Background` work so as not to get stuck baking in the middle of a frame | 2026-10-13 |
| 17 | Purity exception | `alloca` (builds C via `cc`) via `criterion` 0.8 is accepted | An unconditional `criterion` dependency on Windows/Unix (it varies the stack during measurements) that cannot be disabled with a feature. Only a dev dependency of the `pragma_jobs` benches; `deny.toml` excludes the dev graph, `layers.toml` has it in `[purity.accepted]` | 2026-10-13 |
| 18 | Allocation-free graph frame | Dataflow on `ArrivalCounter` (`pragma_sync`): ready tasks are launched via `join` (a stack slot), not `spawn`; the whole frame is one `scope`. The pool's external slot context is cached per thread; the scope counter cache reuses a counter at zero without requiring `strong_count == 1` | `spawn` and `Scope::spawn` allocate a `Box` per task (~90 ns on Windows). Every entry of the main thread into the pool created an `Rc<WorkerCtx>`, and the race "the counter is already zero, but an `Arc` clone is still alive in the tail of `decrement`" drained the counter cache (~1 allocation per frame). After zero, the tail of `decrement` does not change the counter, so a spurious wakeup of waiters is harmless. The cached context holds the last pool's `Arc<Shared>` until the next entry (memory only, pool threads are not held back) | 2026-10-13 |
| 19 | `unsafe` in a `pragma_graph` test | A counting `GlobalAlloc` in `tests/alloc.rs` (delegates to `System`) | The M2 criterion "an allocation-free frame" can be machine-checked only with a global allocator. Test code that never reaches the library; the alternative is an external crate for 20 lines | 2026-10-13 |
| 20 | Purity exception | `libfuzzer-sys` (C++ libFuzzer) only in the separate `fuzz/` workspace | Roadmap M2 requires fuzzing the graph builder; cargo-fuzz is the standard. `fuzz/` is excluded from the workspace and is part of neither the `cargo deny`/audit graph nor users' dependency trees. The same oracle runs in proptest on Windows, where libFuzzer does not link without cargo-fuzz | 2026-10-13 |
| 21 | `pragma_graph` benches | `criterion` (and with it `alloca`, #17) is also a dev dependency of `pragma_graph` | The frame graph is on a hot path (CONTRIBUTING: a benchmark is mandatory); the same conditions as in #17 | 2026-10-13 |
| 22 | Graph resources | `Resources`: a value per type in an `RwLock` slot, accessed in the frame via `try_read`/`try_write`; `run(&mut self, …, &mut Resources)` | No `unsafe`: the graph proves at build time that accesses do not overlap, so locks are never waited on, and a busy slot is a `BorrowConflict` error instead of a race. `&mut` rules out a parallel frame of the same graph and foreign borrows of resources during a frame | 2026-10-13 |
| 23 | Async I/O model | No reactor: synchronous I/O (`std::fs`) goes to the bounded blocking pool of `pragma_async` (`Executor::unblock`). Threads on demand up to `blocking_threads` (4), queued tasks at most `blocking_capacity` (1024); beyond the limit, immediately `AsyncError::Overloaded`. A blocking task is an `async-task` `Runnable`; `async-task` itself wakes the waiting future | File I/O on Windows and Linux is synchronous; IOCP/io_uring mean platform `unsafe` code and a reactor for a gain that asset loading does not have. Separate threads keep a long `read` from occupying frame workers; the queue limit makes an allocation whose size the input sets happen only under a limit (reliability §1). Overflow does not block the caller (the frame). Dropping the executor cancels tasks not yet taken and `join`s the threads; running ones finish, since a synchronous call cannot be interrupted | 2026-10-14 |
| 24 | Scheduling async into the pool | `pragma_jobs::Spawner`: a `Weak` to the pool + `spawn_detached(priority, f)`. A `Runnable` goes into the pool as a `Job::Boxed` with `Background`. Once the pool begins shutting down, the task is dropped (`Cancelled`); the race with an already stopped pool is closed by the `stopped` flag + a pair of `fence(SeqCst)` with `Drop` | `pragma_jobs` does not depend on `async-task`. The `Weak` breaks the cycle "pool queue → `Runnable` → schedule function → pool". Dropping a `Runnable` is regular cancellation in `async-task`; the waiter gets `Cancelled` instead of hanging. In `Drain` mode a background task that keeps rescheduling itself does not hold the pool shutdown forever. A `Box` per scheduling (~90 ns on Windows) is acceptable for background tasks; the frame's hot path does not use it | 2026-10-14 |
| 25 | Blocking async wait | `AsyncHandle::wait` from pool work (a worker or an external thread inside `scope`/`join`, i.e. also a graph frame) immediately returns `AsyncError::WouldBlock`; the bridge into the frame is `poll_ready()` | The rule "no `block_on` in frame tasks" is checked by the machine rather than by review: on a single worker such a wait would hang the pool (only workers run background work), on many it would delay the frame. The check is `Spawner::in_pool_context` (worker TLS, no allocations) | 2026-10-14 |
| 26 | The `frame_sim` vertical slice | The `examples/frame_sim` crate is a workspace member, layer 5 in `layers.toml`, `publish = false`, depends only on the `pragma_core` facade. The background load is applied at a tick known in advance (`load_apply_tick`): one that is ready earlier waits in a buffer, a late one is waited for by the main thread between frames | The example goes through the same lints, layer audit and tests as the library and is invoked in CI as `cargo run -p frame_sim -- --verify 1,4`. Applying at a fixed tick makes the hash independent of when I/O finishes without excluding the load from the hash; `--verify` checks both paths (in time / late) | 2026-10-14 |
| 27 | Platform layer | A new crate `pragma_sys` (L1, `unsafe_allowed`): thread names, priorities, affinity via `windows-sys` (Windows) and `libc` (Linux); `pragma_jobs` exposes it as `pragma_jobs::sys` and stays `forbid(unsafe_code)`. Refines #6: `unsafe` now lives in two crates | The user's choice among three options (a new crate / a `pragma_sync::sys` module / external `thread-priority`+`core_affinity`). `pragma_sync` stays primitives under loom/Miri; Miri does not execute FFI, so it has its own tests on a real OS and a clippy cross-check under Linux. | 28 | Task context for crash reports | A task label is a frame on the stack of `pragma_sync::run_labeled`; TLS holds only a pointer to the innermost frame (the chain goes through pointers to outer frames). Reading is `current_label(|label| …)`: the label is borrowed for the duration of the closure, `!Send`. Labels are set on graph tasks, `spawn`, `scope`, `detached`, async, `unblock`; not on the second branch of `join` | The panic hook and crash handler read the name without allocations or locks, before `abort`. The `unsafe` (dereferencing the frame) is in `pragma_sync`, under Miri. `join` is a hot path (the M4b target is ≤ 2× rayon), and its "join b" label would say nothing. | 29 | Profiling and watchdog | The `puffin` feature with puffin **0.19.1** without default features; the watchdog only under `cfg(debug_assertions)`, a cell per pool thread with the name in a 64-byte buffer | puffin is pure Rust (`parking_lot`, `itertools`, `byteorder`, `anyhow`); we do not enable `zstd`; 0.20 requires Rust 1.92 > MSRV 1.88. | 30 | Nested `join` (M1 debt) | `pragma_sync::join_on_stack`: the second branch is a frame on the owner's stack with a latch (`AtomicUsize`: PENDING/SLEEPY/SET), with no `Arc` and no scope counter. A branch that was not stolen the owner takes back with its own `pop` and runs inline (zero RMW); a thief sets the latch with a single `swap` and, if the owner announced sleep (`prepare_park`, a CAS), returns its index, and the pool wakes it through the participant's `Unparker`. Every external slot has its own `Parker` (it travels with the slot's queues). A thread outside the pool without a slot takes the old path through a scope. Before stealing, `Stealer::is_empty` (without `epoch::pin`); a worker registers in `crossbeam-epoch` once at startup | The old `join` through `scope` did ~10 atomic RMWs/fences (counter cache, `claimed.swap`, `increment`, cloning and dropping an `Arc`, `decrement` with `waiters.fetch_add(0)`); fib(20) was 4.6–5.5× rayon. The new one: 197–207 µs vs ~100 µs (≤ 2×, `docs/perf.md`). After the `swap` the thief does not touch the frame, so the owner may return immediately (loom model `stack_join_owner_never_misses_thief`, Miri). A `pop` of someone else's task (ours was stolen) runs it right away, as rayon does. Almost all victims on a search round are empty, and crossbeam's `steal` enters an epoch before checking the length. Registering in the epoch allocates a handle in TLS: without the initial steal it happened in the middle of a frame (caught by `tests/alloc.rs`) | 2026-10-14 |

| 39 | Pool startup | `ThreadPool::new` returns once every worker has finished thread initialization: priority and affinity applied, an empty steal (registration in `crossbeam-epoch`, #30), `Rc<WorkerCtx>` in TLS (and with it the thread's TLS destructor list).
